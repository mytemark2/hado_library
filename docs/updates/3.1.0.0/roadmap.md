# 覇道ライブラリ 3.1.0.0 開発ロードマップ

## 0. 文書の位置づけ

この文書は、覇道ライブラリ 3.1.0.0 開発の全体方針・Update順序・完了ゲートを定義する正本ロードマップである。

- 開発ブランチ: `feature/app-3.1.0.0`
- 起点ブランチ: `feature/app-3.0.0.0`
- 起点Commit: `1a5ce523053661c3b8d6a8fc5a295ef620196fe6`
- 起点表示版: `3.0.2.0 r170`
- 開発実施環境: ChatGPTデスクトップアプリのCodex
- `3.1.0.0 Update01 r171`から開発・Preview運用を開始し、`r172`で全件条件センサス、`Update02 r173`で正式schemaとEvaluator契約、`Update03 r174`でEffectClauseの決定的生成と全件構造監査を完了した。`Update05 r176`を一度Previewへ反映後、ユーザー指示によりUpdate04を`r177`で先に完了し、Update05を`r178`として再開した。さらにUpdate07を`r179`で先行完了し、Update06を`r180`として実施する。

3.1.0.0は、LR袁紹だけを正しく表示するための個別改善ではない。戦法・技能・状態変化等に含まれる「発動契機・条件・対象・効果・倍率変更・回数制限・抑止条件」を構造化し、詳細、部隊編成、検索、状態変化、型評価、結果サマリーが同じ一次情報を共有できる基盤へ刷新する大型開発である。

## 1. 開発目的

現行データでは、条件が自由文の括弧、`■`、`▼`、`→`、注記等に分散しているため、次の問題がある。

1. 常時効果と条件付き効果の区別が分かりにくい。
2. どの条件がどの効果へ掛かるかを機械的に追跡できない。
3. 部隊編成時に現在成立している条件を判定できない。
4. 検索、状態変化、型評価、結果サマリーが個別に自由文を解釈すると判定差異が起きる。
5. 基礎値と条件成立時の強化値を別効果として扱うと二重計上しやすい。
6. 新武将追加時の未知条件を自動的に検出できない。

3.1.0.0では、自由文を証跡として保持しつつ、意味構造を共通データとして持つ。

## 2. 最重要方針

### 2.1 全件条件センサスを仕様確定より先に行う

LR袁紹を設計基準にしない。現行正本の全データを先に監査し、未知条件を洗い出してからCondition Registry / EffectClause仕様を確定する。

現行派生JSONが示す監査母数は次のとおり。

- 武将: 486件
- 戦法: 465件
- 技能: 653件
- 状態変化: 206件

`hadou_effect_condition_blocks.json` は全体監査の重要な入力として再利用するが、現行の文字列マーカー分類を3.1の意味モデル正本にはしない。

### 2.2 「既知パターンだけ抽出」ではなく残差方式で監査する

全戦法・全技能・関連状態変化の効果文を列挙し、条件・trigger・effect・modifier等へ分類できなかった残差を必ず一覧化する。

```
全原文
  ↓
意味単位へ分割
  ↓
既知構造へ分類
  ↓
未分類残差
  ↓
新条件型 / 説明文 / ノイズを人間が確認
  ↓
Condition Registry更新
```

Update01の完了条件は「多数抽出できた」ではなく、現行正本に存在する条件表現について未確認のものがないことである。

### 2.3 条件・発動契機・対象・効果を混同しない

内部モデルでは最低限次を分離する。

- `context`: どの場面の評価か
- `trigger`: いつ発動するか
- `when`: 何を満たす必要があるか
- `target`: 誰に作用するか
- `effect`: 何が起きるか

`trigger` を通常条件として扱わない。`target` を条件として扱わない。

### 2.4 基礎値と条件成立値はbase + overrideで表現する

例:

- 魁威 25% → 主将時50%
- 戦法威力 250% → 主将かつ兵力50%以上で700%
- 猛奮 50% → 主将時100%

これらを独立効果として二重登録せず、同一効果の基礎値と条件付きoverrideとして管理する。

### 2.5 原文は削除せず、詳細UIでは折り畳み表示を標準とする

構造化表示を主表示とし、取得元の原文は証跡・フォールバックとして保存する。

```
構造化された効果一覧
...
▶ 原文を表示
```

信頼済み構造データを持たない項目は、無理に構造表示せず原文フォールバックを許可する。

### 2.6 判定結果は保存しない

部隊編成localStorageへ条件成立結果を保存しない。保存済み編成情報と最新EffectClauseから都度再計算する。条件定義更新後も古い派生判定が残らないようにする。

### 2.7 UI実装と採点変更を同時に行わない

構造化、表示、編成判定、検索統合を先に安定させ、型評価/scoreEvidenceへの影響はUpdate07まで遅らせる。旧採点との差分をshadow比較してから切り替える。

## 3. 全件センサスで必ず確認する条件・制御の系統

以下は既に現行正本で存在を確認した代表系統であり、Update01ではこれらに限定せず未知型も探す。

### 3.1 配置・編成条件

- 主将 / 副将 / 補佐 / 侍従
- 主将か、主将と自身が好相性
- 副将で主将と好相性
- 主将が男性等の属性条件
- 自部隊が特定兵科
- 特定武将が主将
- 指定武将群のうち1人以上が主将/副将/補佐/侍従にいる
- 主将と副将全員と好相性
- 部隊内の好相性武将人数
- 侍従人数
- 編制時点の攻撃/防御/知力等の閾値
- 兵器を編制している
- 装備・陣形・名馬・軍馬等に依存する条件が存在するか

### 3.2 戦闘中の動的条件

- 現在兵力率
- 自部隊と敵部隊の攻撃/知力/最大兵力等の比較
- 状態変化の有無
- 強化/弱化効果の個数
- 兵器が健在
- 敵主将と特定武将の相性
- 対象が特定状態である

### 3.3 数量・数式条件

- 政治150につきn%
- 技能Lv × n%
- 将星ランクに応じる
- 好相性武将数 × n%
- 侍従人数 × n%
- 強化効果数 × n%
- 連鎖数に応じる
- 最大値、下限、切り捨て、上限、倍率変更

### 3.4 発動契機

- 出陣時
- 交戦開始時
- 主将戦法発動時
- 副将1戦法発動時
- 副将2戦法発動時
- この技能を持つ武将が戦法を発動した時
- 自部隊の副将が戦法を発動する度
- 通常攻撃時
- 通常攻撃を受ける直前
- 戦法攻撃を受ける直前
- 会心攻撃でダメージを与えた時
- 兵器行動時
- 被ダメージ後 / 壊滅しなかった時

### 3.5 ライフサイクル・回数制御

- 出陣後、最初の戦法発動まで
- 出陣中に1度まで
- 1度の通常攻撃につき1回
- 連鎖攻撃ごと
- 戦法発動すると再び発動可能
- 累積値の初期化/リセット
- 効果回数を消費する/しない

### 3.6 抑止・除外・対象選択

- 非攻撃戦法の場合は効果なし
- 絶縁等で攻撃そのものが無効なら発揮しない
- 一定値以下なら固定効果を適用しない
- 特定の強化/弱化/即時効果だけを対象とする
- 好相性部隊を優先して対象にする
- 発生確率を条件で増加/倍化する

### 3.7 別コンテキスト

- 軍事府、参軍府、文化府、民家、田畑、製鉄所、城壁等への任命
- 都市外出等の非部隊編成コンテキスト

これらは部隊編成画面で単純に「不成立」と表示せず、評価コンテキスト外として扱う必要がある。

## 4. 3.1共通意味モデルの暫定原則

最終schemaはUpdate01完了後のUpdate02で確定する。Update01前に固定しない。

概念上は次の要素を候補とする。

```
EffectClause
 ├ context
 ├ trigger
 ├ when
 ├ target
 ├ effect
 ├ modifier
 ├ limit
 ├ reset
 ├ priority
 ├ suppression
 └ evidence
```

`evidence` には少なくとも元エンティティ、元セクション、元技能/戦法、原文を追跡可能な情報を保持する。

条件式はAND/OR/NOTを表現できる構造とし、単純なキーワード配列にしない。

## 5. 条件評価状態

部隊編成等での共通Evaluatorは、最低5状態を扱う。

- `met` → 成立
- `unmet` → 不成立
- `deferred` → 戦闘中判定
- `not_applicable` → 対象外
- `unknown` → 判定不可

AND条件では、明確な不成立が1つでもあれば全体を不成立とする。戦闘中にしか判定できない条件が含まれる場合でも、編成条件が既に不成立なら「戦闘中判定」ではなく「不成立」とする。

## 6. リファレンス/回帰ケース方針

LR袁紹は唯一の設計基準にしない。各条件型を代表する複数ケースをgold setとして固定する。

初期候補:

- LR袁紹: 主将、兵力50%以上、base→override
- LR馬良: 好相性、政治比例、副将1/副将2発動、任命
- LR関平: 特定主将、初回戦法まで、強化数、敵能力比較
- LR孫堅・盾兵: 編制時能力値、兵力、威力固定条件、対象優先
- LR司馬昭: 指定武将集合、敵主将相性、攻撃直前、抑止条件
- LR黄月英: 兵器編制・健在、兵器行動、敵知力比較

Update01で条件型が増えた場合、各新型に最低1件の回帰ケースを追加する。

## 7. Update計画

### Update01 — 全件条件センサス

**目的:** 現行正本に存在する条件・trigger・modifier・limit等の全類型を把握し、未知条件を残したままschemaを固定しない。

**対象:** 武将486、戦法465、技能653、状態変化206を起点とし、関連参照を追跡する。

**実施内容:**

1. 最新正本とSHA、関連派生JSON、クローラー生成処理を再確認する。
2. `hadou_effect_condition_blocks.json` の生成schema、マーカー、誤分類、未抽出を監査する。
3. 全戦法・全技能・関連状態変化を意味単位へ分割する監査手段を用意する。
4. 条件候補だけでなく全原文から未分類残差を抽出する。
5. 条件/trigger/context/modifier/limit/reset/suppression等の類型を整理する。
6. 現行condition blockを持たない戦法・技能も全件個別確認する。
7. gold setを30〜50件以上作成し、各条件型を最低1件含める。
8. 未分類一覧、誤分類一覧、ノイズ一覧、要人手確認一覧を成果物として残す。

**完了ゲート:**

- 対象母数と走査件数が一致する。
- 未走査エンティティが0件。
- 未確認残差が0件。
- 条件型一覧と代表例が文書化されている。
- 現行condition blocksの再利用可否と不足点が記録されている。
- Update02でschemaを決めるための入力が揃っている。

- 状態変化そのものに内在する条件を、付与元戦法/技能と区別して扱う。
- 編成時確定条件と戦闘中動的条件を分離する。
- `met/unmet/deferred/not_applicable/unknown` の評価契約を確定する。

## 10. 3.1開発で禁止する近道

- LR袁紹だけ通る専用パーサを作らない。
- 条件タグだけ作って条件→効果の対応を省略しない。
- triggerを通常条件へ押し込まない。
- targetを条件として扱わない。
- baseとoverrideを別効果として二重登録しない。
- 現行condition markerへキーワードを足し続けるだけで3.1を完成扱いしない。
- 構造化不能な原文を推測で確定扱いしない。
- scoreEvidenceをUI実装と同時に切り替えない。
- 部隊編成で評価できない任命等を「不成立」と誤表示しない。

## 11. 3.1.0.0の完成定義

3.1.0.0は、特定武将の表示が改善した時点では完了しない。

次を満たして初めて完成とする。

1. 現行正本の全条件表現が監査済みである。
2. 新しい条件型を追加可能なRegistry/Clause構造がある。
3. 新武将追加時に未分類条件を検出できる品質ゲートがある。
4. 詳細・編成・検索・状態変化・型評価・サマリーが同じ一次Clauseを共有する。
5. 原文を証跡として辿れる。
6. 保存互換、`file://`、`https://`、PC、スマホを維持する。
7. Actions、イベント駆動Preview、公開確認まで完了している。

このロードマップを3.1開発の正本とし、Update01の全件条件センサス結果によって条件型やschema候補が増えた場合は、実装へ進む前に本文書へ反映する。
