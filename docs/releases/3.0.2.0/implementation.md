# 3.0.2.0 r169 実装内容

## 分類と原因

- 分類: タグ索引の対象属性不足。
- 原因: 既存タグ索引は状態変化の種類・6分類・対象側・方向だけを持ち、個別状態変化とその所有者関係をタグ化していなかった。
- 影響範囲: 通常検索、状態変化検索、型検索で共有するタグ入力・タグ一覧・選択済みタグ・検索判定。

## 恒久対策

- クローラーは状態変化マスター全件と `hadou_related_link_index.json` の正規所有者関係から状態変化タグを生成する。
- `statusEffectTagAudit` でマスター件数、所有者関係、技能タグより前のグループ順を品質ゲート化する。
- アプリは同じ関連リンクから互換タグを構築できるため、旧クローラーによる自動更新直後も機能を維持する。
- 能力変化のタグ値は内部の正規名を保持し、画面では状態変化検索と同じ表示名に変換する。

## 外部化判断

HTMLへロジックを追加せず、タグ処理は既存の `hado_status_effects.js`、生成処理はクローラーの `app.js` に実装する。

## r168 スマホChrome候補選択修正

- 分類: 3.0.2.0 Preview内のスマホ互換性不具合。公開版には未反映。
- 根本原因: タグ候補をブラウザ標準の `datalist` に委ねていたため、スマホChromeでは候補表示と選択イベントの順序が安定しなかった。加えて、入力解決が正規タグ文字列と状態変化別名だけに限定され、`掃討` から一意な `技能:掃討` を解決できなかった。
- 影響範囲: 通常検索・状態変化検索が共有するタグ入力。タグ一覧パネル、選択済みタグ、検索条件のAND/OR判定、派生JSONには影響しない。
- 恒久対策: 独自listboxへ統一し、候補を16件に制限する。一意な表示名を正規タグへ解決し、IME変換中は候補構築を行わない。タップ時は選択済みタグを描画してから検索を遅延実行する。
- 再発防止: `掃討` の一意性、独自listbox、タップ経路、候補件数上限、16px入力、モバイル表示領域を自動検証へ追加する。

## r168 外部化判断

HTMLにはlistboxの最小DOM構造だけを置き、候補検索・選択処理は既存の `hado_status_effects.js`、表示は既存の `hado_styles.css` に実装する。インラインJavaScriptは追加しない。

## r169 候補索引の事前計算

- r168の公開Previewログで、入力ごとに全タグの表示名変換と並べ替えを行い、候補描画に約570ms残ることを検出した。
- タグ索引構築時に、正規タグ・表示名・グループ付き表示名の小文字検索文字列、グループ順位を1回だけ計算する。
- 入力時は事前計算済み文字列の部分一致、簡単なスコア比較、最大16件のDOM生成だけを行う。
- blurの遅延処理には世代番号を持たせ、再フォーカス後に古いタイマーが候補を閉じないようにする。候補pointerdown中も閉鎖を抑止する。
